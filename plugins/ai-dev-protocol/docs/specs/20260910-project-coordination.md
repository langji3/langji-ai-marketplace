# 跨对话与并行需求的流程兼容性 Spec

## 背景与目标

用户可以在项目主对话提前约定需求讨论、spec、独立工作树执行和完成回报。AI Dev Protocol 应配合这些安排，让现有开发流程在跨对话、多需求情况下不冲突。

本次仅修正流程的适用范围和交接行为，不在插件里内建项目协调模式、角色路由体系、派发器或通知机制。保留一个 Router、原有 8 个阶段和现有模板。

核心顺序保持不变：先建立该需求的 AI 分支，再在该分支提交中文 spec；对应内容确认后才实现。

## 本次范围

1. 尊重对话已分配的职责。加载插件不自动改变为协调者或执行者，不因此创建任务；只读探子或审查继续保持原范围。
2. “一个需求”约束实现工作单元和分支，不限制主对话同时讨论或推进多个需求。缺失决策只暂停受影响工作。
3. 新对话接续已有任务时核实分支、spec 版本和适用确认，复用完成的阶段，不因切换对话重复建分支、写 spec 或索要相同确认。
4. 主对话也可能在 AI 分支准备 spec，不能仅凭分支名改变对话职责。新需求从已确定来源分支创建自己的工作单元，不能混入正在执行的需求。
5. 范围变化沿用已有上下文授权规则。用户已明确确认具体 delta 时，按其范围落盘并核实即可，不再重复询问同一决定。
6. 用户要求回报指定对话时，按其既有安排和宿主能力发送现有 handoff；无法发送时提供可转交内容并说明投递未完成。目标标识必须来自已知事实，不能猜测。

## 非目标

- 不定义主对话与功能任务的固定工作模式、调度顺序或默认角色。
- 不新增 PHASE、skill、模板、事件字段、协调索引、任务数据库、运行时脚本或宿主能力抽象。
- 不保证后台运行、自动唤醒或通知到达，不把探索子代理作为用户功能任务的替代。
- 不修改分支先行、spec 确认、合回及 Apifox 写入的现有授权边界。

## 影响区域与实现思路

- Router：少量通用兼容说明，保留原路由。
- requirement-intake / branch-workflow / spec-writing：限定单需求与等待范围，支持复用已有阶段，明确 spec 准备不属于实现代码写入。
- authorization / recovery：跨对话核实并沿用确认，保留用户分配的职责；不新增状态存储。
- handoff：仅补充“用户已要求回报其他对话”的可选行为，复用现有摘要模板。
- README / usage-scenarios：说明这些兼容行为，无需更改安装与宿主 adapters。
